# TCP 与 UDP

## 一句话结论

TCP **面向连接、可靠、有拥塞控制**，代价是慢、头部大；UDP **无连接、不保证可靠、尽力而为**，换来的是快、延迟低、头部小。选谁取决于能不能容忍丢包和重传延迟。

## 标准答案

**核心区别**

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（三次握手、四次挥手） | 无连接，直接发 |
| 可靠性 | 保证不丢、不重、按序 | 不保证，可能丢包、乱序 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有（慢启动、拥塞避免、快重传、快恢复） | 无 |
| 头部大小 | 20 字节（带选项可到 60） | 8 字节 |
| 传输单位 | 字节流（无边界，会粘包） | 数据报（有边界，一次一包） |
| 连接数 | 一对一 | 一对一、一对多、多对多 |
| 速度 | 慢 | 快 |

**适用场景**

- TCP：HTTP/HTTPS、FTP、SMTP（邮件）、SSH、数据库连接。凡是**不允许出错**的都用它。
- UDP：DNS 查询、DHCP、音视频通话、在线游戏、直播、QUIC（HTTP/3 的底层）。这些场景**偶尔丢一帧比等重传好得多**——视频卡一下能接受，但等重传导致的延迟累积会毁掉实时体验。

**UDP 也可以可靠**

可靠性不是 TCP 的专利，可以在**应用层**用 UDP 自己实现：加序列号、确认、重传、排序。QUIC（HTTP/3）就是这么干的——它跑在 UDP 上，但自己实现了可靠传输和拥塞控制，同时避开了 TCP 的队头阻塞问题和握手延迟。

## 原理展开

### TCP 怎么保证可靠

1. **序列号与确认号**：每个字节都有编号，接收方回 ACK 告诉发送方"我收到到哪里了"。
2. **超时重传**：发出后计时，超时没收到 ACK 就重传。超时时间（RTO）动态计算，基于往返时间 RTT 的采样。
3. **滑动窗口**：发送方不必等一个 ACK 再发下一个，而是可以连续发送窗口内的多个报文，窗口随 ACK 向前滑动。**窗口大小 = min(接收窗口, 拥塞窗口)**。
4. **流量控制**：接收方在 ACK 里带上自己的接收窗口大小，发送方据此调整发送速率，避免把接收方缓冲区撑爆。窗口为 0 时发送方暂停（零窗口探测）。
5. **拥塞控制**：发送方根据网络状况（丢包、延迟）主动降速，避免把网络堵死。

### 拥塞控制四个阶段

- **慢启动**：拥塞窗口从 1 个 MSS 开始，**每收到一个 ACK 就 +1**，实际效果是每轮 RTT 翻倍（指数增长）。达到慢启动阈值 ssthresh 后进入下一阶段。
- **拥塞避免**：每轮 RTT 只 +1（线性增长），谨慎探路。
- **快重传**：收到 3 个重复 ACK 就立刻重传丢失的报文，**不等超时**（大幅降低等待时间）。
- **快恢复**：快重传后不回到慢启动（那样太激进），而是把 ssthresh 减半、拥塞窗口设为减半后的值，直接进入拥塞避免。

发生超时重传（比 3 个重复 ACK 更严重的信号）时，才把 ssthresh 减半、拥塞窗口重置为 1，重新慢启动。

### TCP 粘包是怎么产生的

TCP 是**字节流协议**，没有消息边界。发送方写两次 `send("A")` 和 `send("B")`，接收方一次 `recv` 可能拿到 "AB"，也可能只拿到 "A"。原因是：

- Nagle 算法把小包合并发送
- 接收方缓冲区里积压了多段数据
- 网络层拆包重组

**解决办法（应用层自己定边界）**：

1. 定长消息：每个包固定 N 字节，不够补 0（简单但浪费）
2. 分隔符：如 `\n`（要注意内容里不能出现分隔符）
3. **长度前缀（最常用）**：包头 4 字节表示 body 长度，接收方先读长度再读内容

UDP 不会有粘包问题，因为它是数据报协议，一次 `sendto` 对应一次 `recvfrom`，天然有边界。

### TCP 的队头阻塞

TCP 保证按序交付，如果第 2 个包丢了，即使第 3、4 个包到了，应用层也读不到——必须等第 2 个包重传。这就是队头阻塞（Head-of-Line Blocking）。HTTP/2 的多路复用在 TCP 上仍受此影响；HTTP/3 改用 QUIC（基于 UDP），每个流独立，解决了一个流丢包阻塞其他流的问题。

## 面试常问

1. **TCP 比 UDP 慢在哪？** 握手和挥手的往返、确认与重传等待、拥塞控制的保守调速、更大的头部、以及内核协议栈的处理开销。
2. **为什么 DNS 用 UDP？** 查询报文小（通常小于 512 字节），一次请求一次响应，用 UDP 一次往返就完成；用 TCP 光握手就要多一个 RTT。但 DNS 也支持 TCP——响应超过 512 字节或做区域传送时用 TCP。
3. **UDP 怎么实现可靠传输？** 应用层加：序列号、ACK 确认、超时重传、滑动窗口、拥塞控制。参考 QUIC 或 RTP/RTCP。
4. **MSS 和 MTU 的关系？** MTU 是数据链路层一次能传的最大帧（以太网 1500 字节），MSS 是 TCP 层一次能传的最大数据段 = MTU − IP 头（20）− TCP 头（20）= 1460 字节。TCP 握手时双方交换 MSS。
5. **TCP 的 keepalive 和 HTTP 的 Keep-Alive 是一回事吗？** 不是。TCP keepalive 是内核的保活探测（默认 2 小时，用于检测死连接）；HTTP Keep-Alive 是应用层复用 TCP 连接，避免每次请求都重新握手。
