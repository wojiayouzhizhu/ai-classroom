# HTTPS 与 TLS 握手

## 一句话结论

HTTPS = HTTP + TLS。**先用非对称加密安全地协商出一个对称密钥，之后用对称加密传数据**——非对称只用在握手阶段解决"密钥怎么安全送达"，对称加密负责后续高效传输。

## 标准答案

### 为什么不能只用一种加密

- **只用对称加密**：双方要共享同一个密钥，但密钥怎么安全传给对方？如果明文传，中间人截获就能解密全部通信。
- **只用非对称加密**：公钥可以公开，但非对称运算（RSA、ECC）比对称慢几个数量级，全程用会慢到无法接受。

所以实际做法：**非对称协商密钥 + 对称加密数据**。

### TLS 1.2 握手过程（RSA 密钥交换）

1. **ClientHello**：客户端支持的 TLS 版本、密码套件列表、一个随机数 `Client Random`。
2. **ServerHello**：服务器选定的版本和密码套件、一个随机数 `Server Random`、服务器证书（含公钥）。
3. **证书校验**：客户端检查证书链是否可信（是否由受信任 CA 签发）、域名是否匹配、是否过期、是否被吊销。
4. **密钥交换**：客户端生成 `Pre-Master Secret`，用证书里的**服务器公钥加密**后发给服务器。服务器用自己的私钥解密。
5. **生成会话密钥**：双方用 `Client Random + Server Random + Pre-Master Secret` 各自计算出相同的**主密钥（Master Secret）**，再派生出会话密钥。
6. **握手完成**：双方互发 `Finished` 消息，用会话密钥加密，验证握手没被篡改。之后进入对称加密数据传输。

关键点：**Pre-Master Secret 只有持有私钥的服务器能解开**，中间人即使截获所有报文也拿不到它，因此算不出会话密钥。

### 为什么需要三个随机数

只用 Pre-Master Secret 的话，如果客户端的随机数生成器有问题（生成了可预测的值），密钥就可被破解。加入双方各自的随机数后，密钥由三方输入共同决定，**任何一方随机性不足都不会导致密钥可预测**。

### 证书链与 CA 信任

浏览器/操作系统内置了一批**根 CA 证书**（自签名的公钥）。服务器证书由中间 CA 签发，中间 CA 由根 CA 签发，形成链条。验证时从服务器证书逐级向上，看能否链到某个内置的根 CA——能链上就信任。这叫**信任链**。

自签名证书不在链里，所以浏览器会警告（这也是抓包工具要手动安装根证书的原因）。

### TLS 1.3 的改进

- **1-RTT 握手**：把密钥交换提前到 ClientHello（客户端直接猜服务器会选的密钥交换算法并发公钥），省掉一个往返。
- **0-RTT**：会话复用时，第一次握手后可以缓存密钥，下次直接带数据发（有重放风险）。
- **砍掉不安全的算法**：不再支持 RSA 密钥交换、静态 DH、RC4、SHA-1 等，只保留前向安全的（EC）DHE。
- **前向安全成为强制**：RSA 密钥交换被废弃，因为一旦服务器私钥泄露，之前所有被截获的通信都能被解密；而 ECDHE 每次握手生成临时密钥对，私钥泄露不影响历史会话。

### HTTP 状态码速记

| 类别 | 含义 | 常见码 |
|---|---|---|
| 1xx | 信息 | 101 协议切换（WebSocket） |
| 2xx | 成功 | 200 OK、201 Created、204 No Content、206 Partial Content（断点续传） |
| 3xx | 重定向 | 301 永久重定向、302 临时重定向、304 Not Modified（命中缓存） |
| 4xx | 客户端错误 | 400 请求错误、401 未认证、403 无权限、404 不存在、405 方法不允许、429 请求过多 |
| 5xx | 服务器错误 | 500 内部错误、502 网关错误（上游返回无效响应）、503 服务不可用、504 网关超时 |

**301 与 302 的区别**：301 永久，浏览器会缓存重定向结果，下次直接跳；302 临时，每次都要问服务器。SEO 上 301 会转移权重。

**401 与 403 的区别**：401 是"你没登录/认证失败"，403 是"你登录了但没权限"。

## 原理展开

### 中间人攻击与证书校验的必要性

如果客户端不校验证书，攻击者可以伪装成服务器发一个自己的证书（假公钥），客户端用假公钥加密 Pre-Master Secret，攻击者用自己的私钥解开，再转发给真服务器——全程透明代理，通信内容全泄露。

校验证书（签发机构、域名、有效期、吊销状态）就是为了确认"这个公钥确实是目标服务器的"，堵死这条路。

### 数字签名怎么保证证书不被篡改

CA 对证书内容做哈希，再用**自己的私钥**加密这个哈希，得到签名附在证书上。客户端拿到证书后：

1. 用 CA 的公钥解密签名，得到哈希值 H1
2. 自己对证书内容做哈希，得到 H2
3. H1 == H2 说明内容没有被篡改，且确实是这个 CA 签的（只有 CA 有私钥能生成这个签名）

注意方向：**加密用公钥、签名用私钥**。这是很多人搞混的点。

### 对称加密为什么快

对称加密（AES）是位运算和查表，现代 CPU 有 AES-NI 硬件指令，速度可达 GB/s 级；非对称（RSA 2048）涉及大数模幂运算，慢几个数量级，且密钥越长越慢。所以只用它交换几十字节的密钥，性价比最高。

### HTTPS 就一定安全吗

HTTPS 解决了**传输过程**的窃听和篡改，但不解决：

- 客户端本身被入侵（装了恶意根证书，如公司监控、抓包工具）
- 服务器被攻破
- 用户在钓鱼网站上主动输入密码（证书是合法的，域名也确实是攻击者注册的相似域名）

## 面试常问

1. **HTTPS 握手用了几种加密？** 非对称（RSA 或 ECDHE，用于交换 Pre-Master Secret）+ 对称（AES 等，用于后续数据传输）+ 哈希（用于完整性校验和数字签名）。
2. **为什么需要 CA？** 没有可信第三方就无法确认"公钥属于谁"，任何人都能自称是目标网站。CA 就是这个可信第三方。
3. **银行 U 盾为什么安全？** 私钥存在硬件里无法导出，签名在硬件内完成，即使电脑中毒也拿不到私钥。
4. **HTTPS 抓包原理？** 抓包工具（Charles、Fiddler）生成自己的根证书并安装到系统信任列表，然后做中间人：对客户端伪装成服务器，对服务器伪装成客户端。前提是**用户手动信任了这个根证书**——所以 HTTPS 抓包能成功，恰恰是因为你主动破坏了信任链。
5. **WebSocket 和 HTTP 什么关系？** WebSocket 借 HTTP 完成握手（请求带 `Upgrade: websocket`，服务器回 101），之后切换到 WebSocket 协议，建立全双工长连接。
