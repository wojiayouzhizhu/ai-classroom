# TCP 三次握手与四次挥手

## 一句话结论

三次握手是为了**确认双方收发能力都正常并同步初始序列号**；四次挥手是因为 TCP 是全双工的，每个方向都要单独关闭，被动关闭方的 ACK 和 FIN 无法合并发送。

## 标准答案

### 三次握手过程

1. **第一次**：客户端 → 服务器，`SYN=1, seq=x`。客户端进入 `SYN-SENT`。
2. **第二次**：服务器 → 客户端，`SYN=1, ACK=1, seq=y, ack=x+1`。服务器进入 `SYN-RCVD`。
3. **第三次**：客户端 → 服务器，`ACK=1, seq=x+1, ack=y+1`。双方进入 `ESTABLISHED`，可以开始传数据。

### 为什么必须是三次，不是两次

**两次握手无法确认客户端的接收能力和服务器的发送能力，更关键的是无法防止历史连接的重复初始化。**

假设用两次握手：客户端发出一个 SYN，因网络拥塞迟迟没到，客户端超时重发一个新的 SYN 并建立连接、传完数据、关闭了。这时那个老的 SYN 终于到达服务器，服务器以为是新连接请求，直接回 SYN+ACK 并进入 ESTABLISHED（两次握手下服务器发完就算建立成功）。但客户端根本不认这个连接（序列号对不上），不回 ACK，服务器却已经分配了资源在傻等——白白浪费。

三次握手下，服务器收到老 SYN 后回 SYN+ACK 只是进入 `SYN-RCVD`（半连接状态），必须收到客户端第三次 ACK 才建立。客户端发现 ack 对不上会回 RST，服务器就释放资源。

一句话记忆：**三次握手让"分配的初始序列号"这件事由双方共同确认，避免单方面误判。**

### 四次挥手过程

1. **第一次**：主动方 → 被动方，`FIN=1, seq=u`。主动方进入 `FIN-WAIT-1`（不再发数据，但还能收）。
2. **第二次**：被动方 → 主动方，`ACK=1, ack=u+1`。被动方进入 `CLOSE-WAIT`。主动方收到后进入 `FIN-WAIT-2`。
3. **第三次**：被动方处理完剩余数据，发 `FIN=1, seq=v`。被动方进入 `LAST-ACK`。
4. **第四次**：主动方 → 被动方，`ACK=1, ack=v+1`。主动方进入 `TIME-WAIT`，等 2MSL 后关闭；被动方收到 ACK 立即关闭。

### 为什么挥手要四次，握手只要三次

因为握手时服务器可以把 `SYN` 和 `ACK` 合并成一个报文（第二次握手）——服务器收到 SYN 后没有数据要发，可以立刻同步自己的序列号。

而挥手时，被动方收到 FIN 只能**立即回 ACK**（这是协议要求，不能延迟），但它可能还有数据没发完，不能马上发 FIN。等数据发完了才发自己的 FIN。所以 ACK 和 FIN 分成了两次，总共四次。在被动方确实没有数据要发的情况下，ACK 和 FIN 也可能合并，变成三次挥手。

### TIME_WAIT 为什么要等 2MSL

MSL（Maximum Segment Lifetime）是报文最大生存时间，通常 30 秒或 1 分钟。等 2MSL 有两个目的：

1. **可靠地终止连接**：保证最后一个 ACK 能到达对方。如果这个 ACK 丢了，被动方会重发 FIN，主动方还在 TIME_WAIT 就能重回 ACK。如果不等直接关闭，对方永远收不到 ACK，会一直重发 FIN。
2. **让旧连接的残留报文在网络中消散**：避免相同四元组（源IP、源端口、目的IP、目的端口）的新连接收到上一个连接的迟到报文，造成数据错乱。

### TIME_WAIT 过多怎么办

服务器出现大量 TIME_WAIT 通常是自己主动关闭了连接（比如 HTTP 短连接的服务端）。处理方式：

- 让客户端主动关闭（服务端被动关闭不产生 TIME_WAIT）
- 开启连接复用（HTTP Keep-Alive、连接池）
- 内核参数 `tcp_tw_reuse`（允许复用 TIME_WAIT  socket，需配合时间戳）
- 缩短 MSL（不推荐，有风险）

注意 `tcp_tw_recycle` 在新内核已废弃，NAT 环境下会导致连接失败，不要乱开。

## 原理展开

**握手时的序列号为什么是随机的**

初始序列号（ISN）不能固定从 0 开始，否则攻击者可以伪造报文（猜出序列号就能劫持连接），而且相邻连接可能互相干扰。现代系统 ISN 是基于时钟的伪随机数，随时间递增。

**SYN Flood 攻击与半连接队列**

攻击者只发 SYN 不回第三次 ACK，服务器的半连接队列被占满，正常用户建不上连接。防御手段：

- **SYN Cookie**：服务器收到 SYN 后不分配资源，而是把连接信息编码进初始序列号里发回去；收到第三次 ACK 时才根据 cookie 还原并分配资源。这样半连接队列不会溢出。
- 增大半连接队列、缩短 SYN 超时重试次数。

**握手过程中的丢包会怎样**

- 第一次 SYN 丢：客户端超时重传（间隔 1s、2s、4s…），约 1 分钟后放弃。
- 第二次 SYN+ACK 丢：客户端以为自己的 SYN 没到，重发 SYN；服务器也在等第三次 ACK，超时后重发 SYN+ACK。
- 第三次 ACK 丢：服务器没收到 ACK，会重传 SYN+ACK；客户端已进入 ESTABLISHED，发数据时带着 ACK，也能补上。

## 面试常问

1. **握手能携带数据吗？** 第一次、第二次不行（还没建立连接）。**第三次可以**——客户端已确认服务器收发正常，可以带数据。
2. **TCP 为什么是三次不是四次？** 服务器的 SYN 和 ACK 可以合并，没必要拆成两次；两次又不够（无法防止历史连接）。
3. **close_wait 过多说明什么？** 被动方收到 FIN 后一直不调 close()，说明**程序里有连接泄漏**（忘了关 socket）。这是代码 bug，不是内核参数问题。
4. **MSL 和 TTL 的区别？** MSL 是报文在网络中的最大生存时间（TCP 层概念，时间单位）；TTL 是 IP 头的跳数限制（每经过一个路由器减 1，到 0 丢弃）。
