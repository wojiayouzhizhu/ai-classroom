# 进程调度算法

## 一句话结论

调度算法的目标是在**周转时间、响应时间、吞吐量、公平性**之间做权衡。实时系统用优先级抢占，分时系统用时间片轮转，通用系统用多级反馈队列兼顾交互与批处理。

## 标准答案

**评价指标**

- **周转时间** = 作业完成时间 − 提交时间（越小越好，批处理看重）
- **响应时间** = 首次被调度的时间 − 提交时间（交互系统看重）
- **等待时间** = 周转时间 − 实际运行时间
- **吞吐量** = 单位时间完成的作业数

**经典算法对比**

| 算法 | 规则 | 抢占 | 优点 | 缺点 |
|---|---|---|---|---|
| 先来先服务 FCFS | 按到达顺序 | 否 | 简单、公平 | 长作业堵住短作业（护航效应），对短作业极不友好 |
| 短作业优先 SJF | 选预计运行时间最短的 | 否 | 平均周转时间最优 | 长作业可能饥饿；运行时间难预知 |
| 最短剩余时间优先 SRTN | SJF 的抢占版 | 是 | 平均周转时间更优 | 同样有饥饿问题 |
| 时间片轮转 RR | 每个进程用完时间片就换下一个 | 是 | 响应快，适合交互 | 时间片太小切换开销大，太大退化成 FCFS |
| 优先级调度 | 按优先级 | 可抢占可不可 | 能体现任务重要性 | 低优先级饥饿（用**老化**缓解：等待越久优先级越高） |
| 多级反馈队列 MLFQ | 多个优先级队列，新进程进最高级，用完时间片就降级，等待久了升级 | 是 | 兼顾响应时间和周转时间，无需预知运行时间 | 参数调优复杂 |

**多级反馈队列（MLFQ）为什么是通用系统的主流**

它解决了"SJF 需要预知运行时间"这个死结：不需要预知，而是**用历史行为推测**——如果一个进程反复用完时间片（说明是 CPU 密集的长作业），就降到低优先级队列；如果进程经常在时间片用完前主动放弃 CPU（说明是 IO 密集的交互式进程），就保持或提升优先级。UNIX、Windows、Linux 的调度器都带有这一思想。

**Linux 的 CFS（完全公平调度器）**

不用时间片，而是给每个进程记录一个"虚拟运行时间"（vruntime），每次调度选 vruntime 最小的进程运行。vruntime 的增长速度与进程优先级成反比——优先级越高，vruntime 涨得越慢，得到的 CPU 越多。用红黑树维护，选最小值的复杂度是 O(log n)。

## 原理展开

**时间片大小怎么定**

经验法则：时间片应该略大于一次典型交互（如一次系统调用）的耗时，通常 10~100ms。太小：上下文切换开销占比过高（切换本身要几微秒到几十微秒，还要污染 Cache）。太大：响应变慢，且退化成 FCFS。

**抢占式与非抢占式**

- 非抢占：进程一直运行到主动放弃 CPU（阻塞或结束）。实现简单，但一个长作业会让后面的短作业等很久。
- 抢占：调度器可以强行剥夺 CPU。响应快，但需要处理临界区、共享数据的保护问题。

**实时调度**

硬实时系统（如汽车电子、飞控）要求任务必须在截止时间内完成，用**速率单调调度 RMS**（周期越短优先级越高）或**最早截止时间优先 EDF**（谁的截止时间近谁先跑）。这与通用系统的"尽量公平"思路完全不同——实时系统要的是可预测性。

**多核调度要额外考虑什么**

1. **负载均衡**：别让一个核忙死另一个核闲着
2. **CPU 亲和性**：进程在某个核上跑过后 Cache 是热的，尽量别迁移到别的核（Cache 冷启动代价大）
3. ** NUMA 架构**：访问本地内存的延迟远低于跨节点访问，调度时要考虑内存就近

## 面试常问

1. **SJF 为什么平均周转时间最优？** 把短作业往前挪，能减少后面所有作业的等待时间总和——可以用交换论证证明：交换任意相邻的逆序作业对，总等待时间只会下降。
2. **怎么解决优先级调度的饥饿？** 老化（Aging）：随着进程等待时间增长，动态提升其优先级，最终一定能被调度。
3. **RR 的时间片设为多少合适？** 20~50ms 是常见取值，要大于一次上下文切换耗时的一个数量级以上。
4. **进程切换和线程切换开销差在哪？** 进程切换要换页表、刷 TLB，线程切换不用（见「进程与线程」）。
