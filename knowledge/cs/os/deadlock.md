# 死锁

## 一句话结论

死锁是**多个进程因竞争资源而相互等待，若无外力干预谁都无法推进**的永久阻塞状态。产生必须同时满足互斥、请求与保持、不可剥夺、循环等待四个条件，破坏任意一个即可预防。

## 标准答案

**四个必要条件（缺一不可）**

1. **互斥条件**：资源同一时间只能被一个进程占用。
2. **请求与保持条件**：进程已持有至少一个资源，又去请求新资源，且不释放已持有的资源。
3. **不可剥夺条件**：资源只能由持有者主动释放，不能被强行抢占。
4. **循环等待条件**：存在一个进程与资源的循环等待链，每个进程都在等待下一个进程持有的资源。

**四种处理策略（按强度递增）**

| 策略 | 做法 | 代价 |
|---|---|---|
| 预防 | 破坏四个条件之一，从根上不让死锁发生 | 资源利用率低 |
| 避免 | 每次分配前判断"是否会让系统进入不安全状态"（银行家算法） | 需要预知资源需求总量 |
| 检测 | 允许发生，定期用资源分配图检测，发现后处理 | 检测有开销 |
| 解除 | 检测到后，撤销进程或剥夺资源 | 已做的工作可能白费 |

**预防的具体做法**

- 破坏互斥：用假脱机（Spooling）把独占设备改造成可共享的（如打印队列），或者用无锁编程（CAS、原子变量）。适用范围窄。
- 破坏请求与保持：**一次性申请所有资源**，申请不到就一个都不拿。简单但资源浪费严重，且很多场景无法预知需要哪些资源。
- 破坏不可剥夺：申请不到新资源时，主动释放已持有的全部资源。实现复杂，已做的工作要回滚。
- 破坏循环等待：**资源有序分配法**——给所有资源类型编号，规定每个进程必须按编号递增的顺序申请。这是工程上最常用、成本最低的做法。

**银行家算法（避免）**

核心思想：每次分配前模拟分配，判断系统是否仍处于"安全状态"——即存在一个进程序列，使得按这个序列执行，每个进程都能拿到所需全部资源并顺利结束。存在这样的序列就分配，否则拒绝。需要预先知道每个进程的最大资源需求量。实际系统很少用（需求量难预知、进程数动态变化），但它是面试高频考点。

## 原理展开

**资源有序分配为什么能破循环等待**

假设有两个进程都要拿锁 A 和锁 B。如果允许各自按自己的顺序申请，就可能出现"P1 拿着 A 等 B、P2 拿着 B 等 A"的环。但如果规定必须先申请编号小的（比如 A=1、B=2），那么任何进程要拿 B 之前必然已经拿到了 A，此时持有 B 的进程不可能还在等 A（因为它拿 B 时 A 已在手），环就构造不出来。

对应到代码里就是：**固定加锁顺序**。这是解决数据库死锁和多线程死锁最常用的手段。

**活锁与饥饿的区别**

- **死锁**：都在等，谁也不动，占有资源。
- **活锁**：都在动，但互相谦让导致谁也拿不到资源（比如两个进程检测到冲突后同时退让、又同时重试）。
- **饥饿**：某个进程长期得不到所需资源，但系统整体还在推进（如优先级调度里低优先级进程永远排不上）。

**死锁检测：资源分配图**

用有向图表示：进程 → 资源是请求边，资源 → 进程是分配边。如果图中存在环，且环上每个资源类只有一个实例，那么一定死锁；如果资源类有多个实例，有环只是"可能死锁"，需要进一步化简判定。

**解除死锁的三种手段**

1. 撤销所有死锁进程（最粗暴）
2. 逐个撤销死锁进程，每撤一个检测一次，直到解除（按代价最小的顺序撤）
3. 资源剥夺：从某些进程强行拿走资源分配给其他进程（要考虑被剥夺进程的回滚）

## 面试常问

1. **数据库里怎么避免死锁？** 固定加锁顺序（同一个事务里按相同顺序访问表）、减小事务粒度、设置锁等待超时（`innodb_lock_wait_timeout`）、用乐观锁。
2. **写一个必然死锁的代码？** 两个线程，一个 lock1→lock2，另一个 lock2→lock1，中间加 sleep 保证交叉。
3. **怎么排查线上死锁？** Linux 下用 `pstack` / `gdb` 看线程的调用栈卡在哪个锁上；Java 用 `jstack` 会自动报 "Found one Java-level deadlock"。
4. **死锁和死循环是一回事吗？** 不是。死循环是进程占着 CPU 一直跑（忙等，CPU 占用高）；死锁是进程阻塞不占 CPU（CPU 占用低，但任务永远完不成）。这是常见的误解。
